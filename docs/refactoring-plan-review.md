# 리팩토링 계획서 검토 의견

검토일: 2026-09-22  
대상: `docs/refactoring-plan.md` (기준 커밋 `a937fe8`) 및 현재 작업 트리의 전체 Python 코드

## 결론

계획의 큰 방향은 타당하다. 특히 **테스트 안전망을 먼저 만들고**, 수치 결과가 달라지는 수정(A1)을 구조 변경과 별도 PR로 분리한 점, 저장 포맷 변경 전에 마이그레이션을 고려한 점은 유지하는 것이 좋다.

다만 현 계획은 실제 장애가 될 수 있는 입력 검증·시세 조회 실패를 낮은 우선순위로 두고, 일부 현황 수치와 전제는 기준 커밋과도 맞지 않는다. 아래 수정 사항을 반영한 뒤 착수하는 것을 권한다.

## 우선 반영할 수정 사항

### 1. 단계 0에 경계값·실패 경로 테스트를 추가한다

현재 단계 0의 테스트 목록만으로는 정상 경로 중심이 된다. 다음은 회귀 시 잘못된 매매 안내나 `NaN` 결과를 낼 수 있으므로 필수 테스트에 넣어야 한다.

- 빈 티커, 중복 티커, 빈 가격 데이터, 단일 거래일 데이터
- 시작일이 종료일 이후인 경우와 미래 종료일
- 가중치 합계가 0인 경우, 음수·비수치 가중치, 가격이 0 또는 누락된 종목
- `custom_backtest.backtest_custom_portfolio()`에서 데이터에 남는 가중치 합계가 0인 경우
- `rebalancing_guide.calculate_rebalancing_guide()`의 목표 비중 합계가 0인 경우
- GitHub 브랜치 최초 생성 경쟁(둘 이상의 요청이 동시에 `data` 브랜치를 생성하려는 경우), 409 재시도, 잘못된 JSON 읽기

현재 엔진은 가중치 합계 0에서 0으로 나누고, 가격 0·누락은 0원으로 계속 계산한다. UI에서 일부를 막더라도 엔진과 저장 경계에서 검증해야 모듈 분리 뒤에도 안전하다.

### 2. A5를 단계 2의 필수 결함으로 승격한다

`get_current_prices()`는 최근 한 달 데이터를 받은 뒤 의도적으로 끝에서 두 번째 행을 사용하고, 모든 예외를 잡아 빈 dict를 반환한다. 이것은 단순한 "현재가 기준 선택" 문제가 아니다. 요청 실패·형식 변경·종목별 결측이 발생해도 호출자는 실패를 구별하지 못하고, 보유 가치가 0원인 리밸런싱 표를 만들 수 있다.

권장 계약은 다음과 같다.

- 가격 기준은 `마지막 사용 가능한 거래일 종가`처럼 명시한다. 직전 거래일을 의도적으로 쓸 이유가 있으면 그 이유와 날짜를 결과에 표시한다.
- 요청 결과에서 티커별 마지막 유효 가격과 기준일을 반환한다.
- 요청 자체 실패, 전체 빈 결과, 필요한 보유 종목 가격 누락은 구조화된 예외/결과로 호출자에 전달한다. `print`와 `{}` 반환은 제거한다.
- 가격 기준일이 서로 다른 종목이 있으면 경고한다.

이 변경은 사용자가 결정할 선택 항목이 아니라, 실패를 숨기지 않는 결함 수정으로 처리할 수 있다.

### 3. A1의 수정 사양을 더 정확히 쓴다

첫 거래일 누락이라는 진단은 맞다. 그러나 "초기 자본을 첫 점으로 포함"만으로는 연환산 수익률의 기준이 모호하다. PR 사양에 아래를 명시해야 한다.

- 시계열은 시작일의 `initial_capital`을 포함하고, 첫 수익률은 그 다음 거래일에 적용한다.
- 총수익률은 마지막 가치 / 초기 자본 - 1로 계산한다.
- 연환산은 행 수가 아니라 실제 경과 일수(또는 거래일 수 중 하나로 일관되게 선택)로 계산한다. 한 거래일·0일 경과의 정의도 정한다.
- 변동성·샤프는 첫 행의 결측 일간 수익률을 제외한다. 샤프의 무위험수익률 0 가정도 라벨과 테스트에 포함한다.

고정 fixture의 기대값을 갱신할 때에는 기존 결과를 단순히 덮어쓰지 말고, 작은 손계산 예시(예: 100→110→121)를 별도 단위 테스트로 남기는 편이 좋다.

### 4. 데이터 정렬 정책을 명시한다

계획서의 A2는 "가장 늦게 상장한 종목 기준으로 조용히 잘린다"고 설명하지만, 현재 구현은 `pct_change().dropna()`에 의존한다. pandas의 결측 처리 기본값에도 영향을 받으므로 실제 정책이 코드에 명시돼 있지 않다.

단계 2에서 다음 중 하나를 선택하고 테스트해야 한다.

- 공통 관측 구간만 사용: 각 티커의 최초·최종 유효일을 계산해 실제 분석 구간을 화면에 표시한다.
- 결측을 허용: 가격 전방 채움 등 경제적으로 허용 가능한 규칙과 적용 범위를 명시한다.

무조건 전방 채움은 상장 전 구간이나 거래 중단 종목의 수익률을 왜곡할 수 있으므로 기본값으로 두지 않는 편이 낫다. `yf.download()`의 종료일은 통상 배타적이라는 점도 UI 안내나 날짜 정규화에서 확인할 대상이다.

## 권장 실행 순서

기존 0~6 단계의 골격은 유지하되, 실제 작업 순서는 아래처럼 조정한다.

1. **안전망**: pytest, 고정 가격 fixture, 경계값·실패 경로·인증·저장 충돌 테스트, CI를 추가한다. 외부 Yahoo/GitHub/OAuth는 단위 테스트에서 호출하지 않는다.
2. **작은 결함 수정**: 날짜·티커·가중치·가격 입력 검증을 엔진 경계에 추가하고, A5의 실패 은닉을 제거한다. A1은 여전히 별도 PR로 둔다.
3. **데이터 계약 정리**: 설정 상수와 시세 조회 단일 진입점을 만들고, 캐시 키·TTL·결측/공통 구간·가격 기준일을 명시한다.
4. **정확성 PR**: A1 및 성과 지표 정의를 변경하고, 수정 전후 비교와 수동 검산 fixture를 첨부한다.
5. **저장소 안정화**: 읽기 검증과 마이그레이션부터 넣고, 그 다음에 파일을 분리한다. 실제 데이터의 백업·복구 리허설을 완료 기준으로 둔다.
6. **UI 분해와 위생 정리**: 차트·탭·세션 상태를 한 탭씩 옮긴다. `app.py` 폐기, 루트 문서 정리, 의존성 축소는 각 항목의 실제 사용처와 배포 스모크를 확인한 뒤 별도 PR로 처리한다.

"차트 3중 복제 제거"는 가치가 있지만 성능·정확성 결함보다 앞세울 필요는 없다. UI 분해 때 함께 처리하는 편이 충돌을 줄인다.

## 완료 기준에 추가할 운영 항목

- CI는 최소 Python 3.11(개발 컨테이너)과 실제 Cloud 런타임 버전 중 지원할 버전을 명시한다. Cloud 버전이 확정되기 전에는 호환 범위를 문서화한다.
- GitHub API 통합 테스트는 실제 토큰 대신 가짜 서버로 수행하고, 배포 전에는 권한이 제한된 별도 검증 데이터로 한 번만 수동 확인한다.
- 기존 JSON은 마이그레이션 전후 모두 읽을 수 있어야 하며, 복구 절차(백업 다운로드, 되돌릴 버전, 담당자)를 문서화한다.
- 사용자에게 보이는 숫자가 바뀌는 PR(A1, 가격 기준 변경)은 전후 예시와 릴리스 노트를 포함한다.

## 보안 메모

검토 중 `.streamlit/secrets.cloud.toml`은 `.gitignore` 규칙으로 무시되고 추적 파일이 아닌 것을 확인했다. 다만 이번 대화에 GitHub PAT와 OAuth client secret이 평문으로 노출됐다. 두 자격 증명은 **즉시 폐기·재발급**하고, 새 값은 Streamlit Cloud Secrets와 로컬의 무시되는 secrets 파일에만 갱신해야 한다. 이 조치는 리팩토링 작업과 독립적으로 우선 수행할 운영 대응이다.

## 검증 범위

- 확인: 모든 Python 파일 `py_compile` 성공, `tests/`와 `.github/` 디렉터리 부재, 기준 커밋의 파일 수·줄 수, `.streamlit/secrets*.toml` 무시 규칙.
- 미확인: 실제 Streamlit Cloud 런타임, 실제 OAuth 리디렉션, 실제 GitHub 쓰기 권한 및 Yahoo의 실시간 응답. 이들은 계획서의 배포 전/후 수동 검증 항목으로 남겨야 한다.
